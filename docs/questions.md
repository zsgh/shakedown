# 需求不明确处的记录与当前实现

> 原则：遇到不明确的地方，**选择最保守的实现**，不自行扩大范围。
> 每条都记录了「问题 / 当前实现 / 待确认点」。

## Q1. skipper（Agent）的对接接口

- **问题**：todo.md 写「与 skipper 现有实现对接，接口待确认」。skipper 仓库目前提供的是
  `skipper.llm.create_llm_client()`（返回 `AsyncOpenAI` 客户端）+ `skipper.drivers.base.AgentDriver`
  （`run(task, sandbox_id, max_turns, timeout) -> dict`）两套接口，与 Shakedown 需要的
  「读知识源 → 抽功能点 → 生成用例 → 归因」并不直接对应。
- **当前实现**：Shakedown 自带 provider 抽象（`LLMProvider.chat / structured`）与工具调用循环；
  `SHAKEDOWN_LLM_PROVIDER=skipper` 时，只复用 skipper 的 **LLM 配置**（base_url / api_key / model），
  走同样的 OpenAI 兼容通道。不依赖 skipper 的 `AgentDriver`。
- **待确认**：skipper 侧是否要提供「知识源检索 + 用例生成」级别的能力？
  如果要，接口形态（同步/异步、输入输出 schema）需要在 skipper 仓库确定后再对齐。

## Q2. OpenAPI 的 `$ref` 外部引用

- **问题**：OpenAPI 允许 `$ref` 指向外部文件（`./common.yaml#/components/schemas/X`）。
- **当前实现**：只解析**文档内部**的 `#/` 引用；外部引用会保留原样（并在解析结果里可见），
  不会报错。
- **待确认**：是否需要支持外部文件引用（需要提供引用根目录或 base URL）。

## Q3. 「鉴权失败」的期望值来源

- **问题**：安全维度用例断言「未鉴权应返回 401/403」，但很多系统返回 404（不泄露资源存在性）
  或 302（跳登录页）。
- **当前实现**：断言期望写成集合 `[401, 403]`；接口**没有声明鉴权要求**时，该断言标记为
  「待确认」（不判失败），避免制造误报。
- **待确认**：是否允许按项目配置「统一期望的鉴权失败状态码」。

## Q4. 边界用例的「依据」判定

- **问题**：边界值（负数、超长、空值）什么时候算「有依据」？
- **当前实现**：生成阶段仍然只根据 spec / 文档里**明确写了约束**（`minimum` / `maxLength` /
  `minLength` / `enum` / 必填）的字段生成已确认边界用例；没有约束就不硬凑，
  改为输出「缺少输入」。
- **失败归因阶段**：允许使用**语义常识**兜底。`name` / `title` / `username` 等标识字段
  被空字符串或纯空白创建/更新成功、负数 `limit` 进入数据库导致 5xx、错误响应泄露
  SQL / 驱动异常，即使文档没有写约束，也判定为缺陷，evidence 标记为 `common_sense`。
- **自动确认**：显式契约违反、5xx、异常泄露、空语义标识被接受，且置信度 ≥ 0.85 时，
  finding 自动置为 `confirmed`，`confirmed_by=auto:attribution`；语义不明确的仍保持
  `pending`，等待人工或外部验证。
- **待确认**：是否把更多项目特有的业务规则配置成显式 `business_rules`，减少常识判断的边界争议。

## Q5. 失败重跑与 flaky 的判定

- **问题**：重跑一次就判 flaky 是否够？连续 3 次全过算不算稳定？
- **当前实现**：失败用例重跑**一次**；两次结果不一致 → `flaky`（不报缺陷）；两次都失败 → `fail`。
- **待确认**：是否需要「重跑 N 次」的可配置策略（当前固定 1 次）。

## Q6. 被测系统的启动方式

- **问题**：todo.md 提到「被测系统启动方式」，但没说由谁启动。
- **当前实现**：平台**不负责**启动被测系统（除 berth 侧的 B11 运行时），
  项目里只记录 `target_start`（docker / command / external）作为说明；
  执行时用 `base_url` 指向已经跑起来的环境。
- **待确认**：是否要让平台负责拉起被测系统（docker compose / systemd）？

## Q7. 项目隔离的「整库重置」

- **问题**：`mode=reset` 时，是每个项目一个独立数据库实例，还是共用实例但不同 schema？
- **当前实现**：优先走 berth 的「一个服务 = 一个实例」（`{项目}-db`）；
  接口自己提交事务时事务回滚无效，所以默认推荐 `mode=prefix`（run_id 前缀 + 事后清理）。
- **待确认**：berth B8（服务重置）落地后，`reset` 模式的具体语义。

## Q8. 报告导出的范围

- **问题**：导出 HTML 报告是否要包含 Agent 轨迹、完整请求响应？
- **当前实现**：单次执行报告包含结果、归因、请求/响应/日志、缺陷与复现命令；
  Agent 轨迹只在看板里看，不进 HTML（体积原因）。
- **待确认**：是否需要「完整版」报告（可选项）。

## Q9. Web 用例的选择器策略

- **问题**：Web 用例的选择器（`#id` / `.class` / 文本）由谁决定？UI 改了怎么办？
- **当前实现**：由 Agent 根据文档 / 代码生成，写在用例里；不做 UI 自愈、不做探索式测试
  （todo.md Phase 6 明确本期不做）。
- **待确认**：是否需要「选择器候选 + 失败时人工更新」的辅助流程。

## Q10. 回测里「误报」的口径

- **问题**：没对上已知 bug 的失败用例都算误报吗？
- **当前实现**：算（`false_positives`）。但注意：**没有依据的断言不判失败**，
  因此误报天然偏低 —— 回测报告里同时给出每个 bug 的命中用例，便于人工复核。
- **待确认**：是否要把「待确认断言」也统计成一种「未判定」结果单列。
