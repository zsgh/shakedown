# 使用手册

以「用户中心」这个真实项目为例，走一遍完整流程。

## 0. 准备

1. 起平台：`docker compose up -d --build`（或本地 `uvicorn` + `npm run dev`）。
2. 打开 http://localhost:5173 → 点右上「新建项目」，三步向导：

### 模型接入

「系统设置 → 模型」：

- `接口地址` 填到 `/v1` 即可（如 `https://opencode.ai/inference/go/openai/v1`）；
  直接粘贴完整 `/v1/chat/completions` 地址也能工作。
- 用 OpenCode Go 时平台会自动带 `x-opencode-session` 和自定义 User-Agent，不需要手配。
- 改完点「测试连通性」：看到「模型服务 · 可用 · 200」再执行；
  404 通常是路径多拼了一层或模型 ID 不对，401 是 key 无效。


| 步骤 | 填什么 |
|---|---|
| 基本信息 | 名称（必填）、被测环境地址（base_url）、描述 |
| 连接知识 | 可选：本地仓库目录，创建后自动导入代码 / 文档 / OpenAPI |
| 确认 | 检查后创建，进入项目总览 |

测试账号、隔离配置、被测库 DSN 在「项目设置」里配置，平台加密存储。

> **项目之间完全隔离**：独立被测库实例、独立账号、独立地址与端口。

> 界面导航：左侧「总览 / 测试设计 / 执行 / 缺陷 / 理解 / Agent 活动」，顶部 `⌘K` 可全局搜索与跳转。

## 1. 绑定知识源

### 方式一：一键自动导入（推荐）

「理解 → 知识源」→ **从仓库自动导入** → 填一个仓库目录（例如 `/Users/you/github/mymac`）→ 自动：

- 识别代码文件 → 建「代码库」知识源（切块 + 抽路由）；
- 识别 Markdown → 建「Markdown 文档」知识源（切块 + 向量）；
- 识别 OpenAPI/Swagger（本地 JSON/YAML）→ 建「OpenAPI」知识源；
- **把文档里的接口清单也解析成接口**：像 `DESIGN.md` 里 `GET /api/health  说明` 这种端点表，
  会被登记成来源为 `doc` 的接口，参与三方对照、给 Agent 提供可引用的依据。

导入结果会列出「导了什么、解析出多少块 / 多少接口、哪个失败了」。

### 方式二：手动逐个添加

1. **Markdown 文档**：给一个目录、单个 `.md` 文件，或**远程 URL** → 按标题层级切块，保留章节路径作为来源位置；
   文档内容 hash 变化后可增量重新解析。
   - GitHub 网页地址（`https://github.com/owner/repo/blob/main/x.md`）会自动转成 raw 地址再拉取；
   - **HTML 页面也能导**（内部 wiki、文档站、渲染后的 README）→ 自动转成 Markdown 再切块；
   - 网络不通时用本地路径即可（仓库已 clone 的情况推荐这么做）。
2. **代码库**：给**本地已 clone 的目录**（不支持 URL）→ 记录 commit hash；按文件/类/方法切块（tree-sitter，
   不可用时退化为行窗口）；抽取路由定义，产出 `endpoint` 候选（来源标记 `code`）。
   已支持 FastAPI/Flask/Spring/Express/Go(ServeMux & HandleFunc & helper 批量注册)/Sinatra/Django/Axum/Laravel 等路由写法。
3. **OpenAPI / Swagger**：给本地 JSON/YAML 文件、URL，或 Swagger UI 页面地址
   （自动探测其背后的 spec 地址）→ 支持 **Swagger 2.0** 与 **OpenAPI 3.0 / 3.1**，
   展开 `$ref`（带循环引用保护），处理 `allOf` / `oneOf` / `anyOf`。

### 非标准接口文档（人能看懂就能导）

接口文档不一定是 OpenAPI。平台的处理方式：

1. **文档里的端点清单**（`METHOD + path + 说明`，在代码块或表格里）→ 自动登记成来源为 `doc` 的接口，
   参与三方对照；
2. **散落在正文里的接口提及**（"创建用户用 `POST /api/users`"）→ 宽松匹配抽出；
3. 上面两招覆盖不了的，交给 **Agent 读文档**：在「接口清单」页点「Agent 抽接口」，
   或在「抽功能点」时自动执行 —— 模型像人一样读文档，产出接口清单并保留原文引用作为依据。

导入后可以在「接口清单」页看到归一化后的接口（method / path / 参数 / 请求体 / 响应 / 鉴权 / 来源）。

## 2. 三方一致性对照

「一致性」页给出 OpenAPI × 代码 × 文档的对照结果：

| 类型 | 含义 |
|---|---|
| 文档独有 | 文档提到、代码与 spec 都没有 → 可能没实现 |
| 代码独有 | 代码有、spec 文档没有 → 可能没同步文档 |
| spec 独有 | spec 有、代码里找不到 → 可能没实现 |
| 参数不一致 | spec 与文档的参数对不上 |

这些条目本身就是**潜在缺陷线索**。

点 **「导出修复清单（.md）」** 可以把不一致项导出成一份任务清单 Markdown：

- 强信号标 **P0**、弱信号标 **P2**，每条带三源证据（代码 `文件:行号` / spec 声明 / 文档原文引用）；
- 每条附**修复指引**——该补 spec、该实现代码还是该补文档，按接口意图判断；
- 修完用统一验收标准核对：重新导入知识源并重算一致性后，该接口变为「一致」。

这份 md 可以直接扔给编码 AI（Claude Code / Cursor 等）按清单修复，AI 无需回到平台查任何信息。

## 3. 抽功能点 + 生成用例

「测试设计」页：

1. 点 **抽取功能点** → Agent 基于文档 + 接口 + 代码产出 `feature`，每个功能点带来源引用；
   无法映射到接口的功能点会标「未映射接口」。
2. 点 **生成用例** → 按四个维度生成。生成完成后，有步骤且至少一条有依据断言的用例
   会自动试运行一次：通过即启用，失败进 `needs_review` + 例外（`auto_validate_generated` /
   `auto_enable_after_validation` 默认开启，可关）。


| 维度 | 内容 |
|---|---|
| 功能 | 每个功能点至少一条正常流用例；断言验证业务结果（状态变化、金额、数据落库） |
| 缺陷/边界 | 空值、超长、负数/零、非法状态跳转、重复提交、精度与时区（只对**有依据**的约束生成） |
| 安全 | 越权访问、未鉴权访问、注入类输入、敏感信息泄露 |
| 性能 | 只做接口级响应时间基线；阈值必须来自文档 / 项目配置 SLA，没有就只记录耗时、把断言标待确认，不硬编阈值 |

生成的用例**默认待确认**（`status=pending`），不会自动执行。

## 4. 审核用例

「测试设计」页默认进入三栏审核工作台：

- 左：功能覆盖树（模块 → 功能点，标出无正常流的功能点）；
- 中：用例列表，可按状态 / 维度 / 功能点 / 标题 / **用例 ID / 缺陷 ID** 筛选，支持分页与多选；
- 右：步骤、断言、预期依据；可直接编辑、AI 补全、单独执行。

逐条或批量 **启用 / 停用**；也可以勾选后 **执行选中**。停用不删除，修改与停用都会写进 `human_feedback`。
键盘：`J/K` 切换、`A` 启用、`X` 停用、`E` 编辑、`/` 搜索。

白盒建议用例（标题以 `[白盒建议]` 开头）初始没有步骤和断言，并在 `missing_input` 里说明缺什么。
右侧点 **AI 补全** 会基于关联 finding、代码位置、接口清单和文档补全步骤 / 断言 / 依据，结果仍为 `pending`，需要人工检查后再启用。
如果自动验证时关联用例仍未启用或不可执行，finding 会标记为「需人工验证」，不会伪造通过。

### 契约缺口

「理解 → 契约缺口」统一汇总所有需要补依据 / 补步骤的用例：

- **待确认断言**：缺少 OpenAPI / 文档 / 代码依据的断言，执行时只记录、不判失败；
- **没有步骤**：无法构造请求，暂时不会进入执行集；
- **待补全说明**：`missing_input` 里的说明，有步骤时不影响执行。

可以逐条点 **AI 补全用例**（只补用例，不改被测系统），也可以 **导出契约缺口报告**（Markdown），交给被测系统的维护者或他们在自己仓库里授权的编码 Agent 去补 OpenAPI 响应 schema、文档或代码证据。

缺口也有处置状态：`待处理 / 已认领 / 已修复待复检 / 接受风险 / 不修复`，可以记录负责人和备注。接受风险和不修复会从默认缺口列表隐藏，但保留审计记录。
接口 / 文档层面的三方差异仍然在「理解 → 三方一致性」里处理。

### 执行状态与批量重新评估

用例列表、详情和缺口列表都会实时返回 `execution_states`，可能同时有多个：

| 状态 | 含义 |
|---|---|
| `never_executed` | 没有任何执行结果 |
| `enabled_no_result` | 已启用但从未执行出结果 |
| `pending_not_enabled` | 仍是 pending，未审核启用 |
| `stale_after_source` | 知识源重新解析后，用例还没有复核 |
| `executed` | 至少有一条执行结果 |

「测试设计」的“执行历史”筛选和「契约缺口」的“执行状态”筛选都支持这些状态，旧的 `never` / `executed` 参数仍然兼容。

缺口页的 **重新评估缺口用例** 会按当前筛选（可再勾选用例）先请求 `POST /api/projects/{id}/cases/enrich` 做 dry-run 预览，确认后才传 `dry_run=false` 入队 `enrich_case` 任务。单次最多 200 条；已在队列/运行中的同用例任务会跳过。批量操作只入队，不直接改用例 spec，也不自动启用。

知识源重新解析后，`reparse_source` 返回 `reevaluate_candidates` 并写入 `KnowledgeSource.meta.reevaluate_candidates`，只提示“有多少条缺说明 / 缺步骤的用例值得重新评估”，不会自动入队。MCP 的 `list_cases` / `list_case_gaps` / `request_case_enrich_batch` 提供同样的筛选和批量能力。

## 5. 执行

顶部 **执行** 或「执行」页的 **执行已启用用例**：

1. **准备环境**：按项目起独立的被测库（berth 服务名 = 项目名 + `-db`）。
2. **编译**：统一 JSON → pytest 代码（写进沙箱 `/workspace`）。
3. **执行**：接口用例用 pytest + httpx，Web 用例用 Playwright（失败截图 / trace）。
4. **失败重跑**：失败用例自动重跑一次；两次结果不一致 → 标 `flaky`，**不报缺陷**。
5. **归因**：Agent 判断失败类别（环境问题 / 用例问题 / 疑似真实缺陷），给出理由与依据；
   疑似缺陷自动生成 `finding`，附复现 curl 命令。

执行中页面每 3 秒自动刷新；顶部有全局任务指示器，完成后弹 toast。

任务最终失败时对应执行会置为 `failed`，不会卡在 `running`；从 Agent 活动页取消执行任务会同步取消对应 Run。失败 / 已取消的任务可在 Agent 活动页直接「重试任务」，执行类会新建一条 Run（保留原用例集合）。

## 6. 看结果

- **总览**：行动中心告诉你下一步该审核 / 看失败 / 分诊缺陷 / 看三方差异，附覆盖率和执行趋势。
- **执行详情**：状态机时间线 + 结果分布；点失败项打开抽屉看请求、响应、断言 diff、日志、归因；
  可人工修正归因、一键重跑失败、导出 HTML 报告。
- **运行对比**：执行页点「对比最近两次」，或运行详情点「对比上次」；按「新失败 / 持续失败 / 已修复 / 新增 / 移除」分组。
- **Spec 版本**：理解 → Spec 版本，任选两个快照对比新增 / 删除 / 变更接口，并列出受影响用例。
- **主题**：侧栏底部可切换深色 / 浅色，选择会记住。
- **缺陷**：待确认 / 已确认 / 误报 / 接受风险 / 不修复；抽屉里看证据、代码位置、复现命令、关联执行、负责人和处置备注。
  外部验证失败（构建产物 / 进程 / 浏览器 / 权限）若没有关联缺陷，会自动生成一条待分诊线索。
- **AI 分诊**：缺陷页点「AI 分诊」，按模块 + 判定分组；可切「按主题」看细分根因。
  AI 只写建议（`cluster_key` / `triage` / `triage_status`），不删除、不覆盖原始 finding；
  每组可展开回原始条目，再批量确认或标记误报。
- **可追溯**：报告里任一结论都能点回用例、执行记录、依据原文。
- **导出**：单次执行报告与项目看板都能导出成自包含 HTML。

### 无人值守控制台

侧栏 **无人值守** 汇总了原先只能在 API / MCP 里使用的能力：

- 运行健康、readiness、CI gate（可指定 run）；
- 调度创建 / 启停 / run-now / 删除；
- 成员与角色（owner / maintainer / viewer）；
- 例外队列处置与 SLA 预览 / 升级 / 强制执行；
- 断言质量、oracle mutation、oracle 趋势、用例退役预览与执行；
- 性能历史、baseline / load / stress / soak 采样；
- 视觉基线、a11y 读取与审计；
- digest / 邮件 / SLA / 变更回归 / flaky / 命令执行等自动化开关。

执行详情页也会显示该 run 的 CI gate 阻断项；契约缺口页可直接跳到断言质量 / 用例退役。

## 7. 白盒走查

「缺陷」页点 **白盒走查**：Agent 按模块读代码，查入参未校验、事务缺失、越权判断缺位、
并发问题、异常吞没、敏感信息日志等，输出带**代码位置（文件 + 行号）**的发现；
无法定位的不输出。白盒发现与黑盒结果分开展示，并会为高风险点生成一条待人工补全的验证用例。

白盒走查是**静态代码审查**，本身不产生执行记录：

- 每条 finding 会关联一条 `[白盒建议] ...` 用例（pending、缺少输入）；
- 补全并启用这条用例、执行后，finding 抽屉会显示「最近执行 #…」回链；
- 同一次代码位置重复走查会复用 finding 和建议用例，不会每次生成一批重复数据；
- Agent 活动里会显示「白盒 2/5 · internal」这类模块进度；
- 白盒走查可以在缺陷页或 Agent 活动里「停止走查」；已完成模块的结果会保留。
  停止后缺陷页会出现「继续走查」，只跳过已完成模块，不从头重跑。

耗时取决于模块数和代码量：一次走查通常包含 5 个模块 × 多轮工具调用，当前默认
工具轮次 5、白盒单独使用 medium 推理。示例项目实测从 7m17s 降到 5m52s。
